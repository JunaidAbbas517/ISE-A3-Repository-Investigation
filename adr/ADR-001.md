# ADR 001 Place academic verification outside the upstream write path

**Status:** proposed and supported by A3 evidence; not implemented.  
**Date:** 25 October 2026.  
**Risk addressed:** R1, direct writes lack the A2 verification/version boundary.

## Context

A1 bounds the problem to verifying changes between official notices and students' personal deadlines. A2 requires owner confirmation, attributable verified evidence, current base version, unchanged state on rejection, and explicit time semantics. Todoman is a personal task CLI. Its edit/save path writes directly to local VTODO storage. P3 demonstrates that two objects read at the same sequence can both save, with the stale one replacing the newer due value. An atomic file replacement prevents a partially written file; it does not provide compare-and-swap semantics, academic authority or revision history.

## Responses considered

| Criterion | A Modify upstream edit/save and storage core | B Separate verification service with controlled export |
|---|---|---|
| Rule ownership | Add candidate, owner, source and revision concepts to the CLI/model | Keep A2 rules in a dedicated service and protected database |
| Change surface | CLI, model, cache, serialization and other write paths must be reconciled | New bounded service and export adapter; original code remains unchanged |
| Existing writers | Every direct/model/synchronization writer must obey new guards | Service owns the authoritative personal record; exported ICS is a derived copy |
| Version safety | Implement coordinated compare-and-swap and history across existing persistence | Enforce a transactional version check in the service; export only committed revisions |
| A4 feasibility | Broad retrofit may exceed a bounded vertical slice | A confirmation endpoint and one export adapter form a possible small slice |
| Cost and residuals | Fork maintenance and compatibility burden | New store, identity mapping and export failure handling are required |

## Decision

Prefer B as the future change boundary. The service would own personal deadline records, not official university deadlines. A request would validate authenticated ownership, independently established source authority, candidate status, expected version and time-zone consistency before committing one history entry. An export adapter would run only after that commit and use a deployment-owned config. No source document would be interpreted as Python configuration.

Todoman would remain a consumer or optional presentation/export target. Numeric cache IDs would not become institutional assignment IDs; a stable mapping to the VTODO UID would be required. External calendar edits would be treated as new unverified input, never silently promoted to the service's verified record.

## Consequences and reversal

This keeps academic rules separate from upstream storage details and preserves the frozen baseline. It does not eliminate work: authentication, a source-authority procedure, a transactional store, safe retries and export reconciliation must still be implemented and tested. If the UI/CLI can modify the derived file directly, the service record remains authoritative and detects/reviews divergence. The study does not claim an export-only adapter can constrain arbitrary external writers.

The A3 rollback boundary is simply to discard generated study workspaces; upstream source is unchanged. A future implementation must disable the adapter without removing the service history and restore its prior release. No database migration or production rollback was executed in A3.

## Evidence and decision triggers

Supporting evidence: P3, `call-trace.json` calls 14–27, source `model.py:1164` and the A2 invariants. Reconsider if a licensed, maintained backend already satisfies the needed ownership/version/source contracts, if a safe data mapping cannot be defined, or if representative users do not find the bounded workflow useful. No performance, user-study or deployment claim supports this decision.
